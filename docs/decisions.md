# 决策与取舍记录

[`plan.md`](plan.md) 是最初的规划。本文件记录实现首版时做出的每一个选择：选了什么、放弃了什么、代价是什么。
标「待确认」的条目是我替你做的暂定选择，改起来成本都不高。

## 0．只读检查真实库后的发现

实现前按计划第一步只读检查了 `~/Documents/Obsidian/ozine`，有三点与规划的假设不一致：

| 发现 | 影响 |
| --- | --- |
| `40 blog` 里还没有真实文章，只有 Quartz 的占位 `index.md` 和空的 `drafts/`、`published/` | 无法用真实文章验证，改用仓库内的模拟库（D1） |
| 附件目录是 `90 system/attachments`，在 `40 blog` **之外** | 只靠 `content` 软链接读不到图片（D5） |
| 现有笔记的图片用标准 Markdown 相对路径 `![](../../90%20system/attachments/x.webp)`，不是 `![[图片]]` | 两种写法都要支持（D6） |

## 1．内容来源与测试

### D1 测试用的模拟库写在测试代码里、运行时临时生成，仓库不保存样本文章

- **选择**：`scripts/export.test.ts` 里定义一个最小的库（博客目录、库外附件目录、库外私密笔记），每个测试把它写入系统临时目录，跑完即弃。
- **放弃**：往真实库里写 mock 文章；以及最初采用的做法——在仓库里放 `fixtures/vault/` 样本目录并提供 `npm run sample` 预览（2026-10-01 删除）。
- **得**：不改动你的笔记；公开仓库里没有看起来像文章的假内容；导出规则（含隐私限制）仍有测试保护。
- **失**：没有了用样本内容预览页面的命令，`npm run dev` 只能看 `published/` 里的真实文章，调样式时可见的排版元素取决于已发布的文章；测试内容不是你的真实写作习惯，可能有没覆盖的语法。

### D2 `content` 软链接指向 `40 blog`（沿用旧 Quartz 项目的指向）

- 已建立，Git 忽略。`40 blog` 下的 `drafts/`、`published/` 子目录只是你的组织方式，程序**不看目录名**，只看 `status`。
- **失**：把文章放进 `published/` 目录不会让它发布，可能与直觉不符。

### D3 缺少 `status` 的文件阻止发布，不设忽略名单（待确认）

- **选择**：严格按规划「缺失或非法状态阻止发布」，内容目录下每个 `.md` 都必须有合法 `status`。
- **放弃**：自动跳过没有 frontmatter 的文件，或维护忽略列表。
- **得**：不会因为漏写字段而悄悄漏发或误发。
- **失**：**当前真实库会被 `40 blog/index.md`（Quartz 占位页）拦下**。我没有改动你的笔记，需要你删除它或加上 `status: draft`。以后想在博客目录放非文章笔记（选题清单等）也都要写 `status: draft`。

## 2．导出规则

### D4 双链、图片在导出时改写；Callout 留到构建时渲染

- **选择**：导出脚本把 `[[双链]]` 改写成 `[标题](/posts/slug/)`、把图片改写成 `![](../assets/x.png)`、删除 `%%注释%%`；`> [!note]` 原样保留，由 Astro 侧的插件渲染。
- **理由**：双链解析需要「文件名 → slug」的全库索引，只有本机有；公开副本必须自洽，Vercel 才能脱离 Obsidian 构建。Callout 本身是合法的 Markdown 引用块，不依赖索引，留在构建侧可以随时改样式而不必重新导出。
- **失**：公开副本不再是原稿的逐字拷贝；Obsidian 语法的处理分散在两处（`scripts/lib/export.ts` 与 `src/plugins/callout.ts`）。

### D5 附件：从软链接的真实路径向上找库根目录，不增加第二个软链接

- **选择**：对 `content` 取真实路径，向上找到含 `.obsidian` 的目录作为库根，再读 `.obsidian/app.json` 的 `attachmentFolderPath`。查找顺序：相对原稿 → 相对库根 → 按文件名在附件目录和博客目录中查找。
- **放弃**：再建一个 `attachments` 软链接；或把附件搬进 `40 blog`。
- **得**：零配置，不改变你现在的附件习惯，原稿里的 `../../90 system/...` 相对路径可以直接解析。
- **失**：程序会读博客目录之外的位置。为此加了三道限制：只导出被已发布文章**实际引用**的文件；只允许图片扩展名（png/jpg/jpeg/gif/webp/svg/avif），笔记无法伪装成附件；真实路径必须在库内。PDF、音视频等附件首版不支持。

### D6 两种图片写法都支持；`![[图.png|300]]` 的尺寸被忽略

- 图片交给 Astro 的图片管线（相对路径 `../assets/`），自动转 WebP、写入宽高、缺图时构建失败。
- **失**：Markdown 语法无法携带宽度，首版不保留 Obsidian 的尺寸设置；非数字的别名会作为替代文字。附件文件名中的空格和括号会被替换为 `-`；不同目录下的同名附件，后者文件名追加内容哈希。

### D7 用逐行状态机 + 正则转换正文，不走 Markdown AST

- **得**：实现短、无额外依赖，未触及的文本逐字保留，报错能给出原稿行号。代码块和行内代码会被跳过。
- **失**：对极端写法不如 AST 严谨（例如缩进代码块里的 `[[...]]` 仍会被当作双链；跨行的行内代码）。真实文章碰到时再考虑换 AST。
- 代码围栏按 CommonMark 判断：结束围栏须与开始围栏同字符、长度不短于它、后面没有其它内容，所以四个反引号的代码块里可以放三个反引号的示例。
- 例外：标题的识别和 id 不走正则，见 D8。

### D8 双链的解析与显示

- 不带路径按文件名匹配，带路径按路径后缀匹配，不区分大小写；范围**仅限博客目录**。
- 指向库内其它目录（如 `30 domain`）的双链按「失效」报错，不会自动公开目标，也不会静默降级成纯文本。**失**：文章里引用自己的知识笔记时必须手动去掉或改写。
- 未写别名时，显示文字用目标文章的 `title` 而不是文件名（文件名是私有的组织方式）。**失**：与 Obsidian 里看到的文字可能不同。
- 标题锚点**不自己解析**：导出时用 Astro 同一个 Markdown 处理器（`@astrojs/markdown-satteri`）渲染每篇已发布文章，直接取它给出的标题 id。渲染前先去掉 `%%注释%%`、把标题里的双链换成公开后的显示文字，让输入与公开副本一致。
  - **放弃**：最初的做法——用正则找 `#` 标题再用 `github-slugger` 计算。它看不到引用块、列表、缩进和 Setext 写法的标题，也处理不好注释、强调、转义，会生成悄悄失效的锚点（2026-10-01 代码审查发现）。
  - **得**：重名编号、Callout 里的标题、各种行内格式都与线上的 id 一致，已用真实构建逐一核对。
  - **失**：导出变成异步，每篇已发布文章多渲染一次；处理器选项必须与 `astro.config.mjs` 里 `satteri()` 的 `features` 保持一致（目前都是默认值），否则两边的 id 可能不同。
  - `[[文章#标题]]` 的匹配忽略大小写、标点和强调标记；同名标题指向第一个。显示文字用标题渲染后的文字。
  - 标题里含双链时，Obsidian 自动补全写出的是文件名（`[[乙#参见 理解接口]]`），而公开后的标题文字是目标文章的 title，两者不同：此时报「找不到标题」，需要手动改成公开后的文字或加别名。
- 不支持：块引用 `[[x#^id]]`、笔记嵌入 `![[笔记]]`（规划已排除）、指向笔记的 Markdown 链接 `[x](y.md)`，三者都明确报错。
- 链接写成绝对路径 `/posts/slug/`。**失**：站点必须部署在域名根路径，不能放在子路径下。

### D9 公开副本的 frontmatter 只保留白名单字段

- 只输出 `title`、`date`、`updated`、`tags`、`description`；`slug` 体现在文件名上，`status` 及其它 Obsidian 属性不输出。
- **得**：私有属性不会随文章进入公开仓库。**失**：以后新增公开字段要同时改导出脚本和 `src/content.config.ts`。

### D10 metadata 细则（待确认）

- 字段与状态名沿用规划的建议值。`draft` / `withdrawn` 只要求 `status` 合法，其余字段可以不全；`published` 必须有 `title`、`slug`、`date`。
- 新增两个可选字段：`updated`（更新日期）、`redirect_from`（见 D12）。
- `tags` 不允许空格、`/`、`#`：首版不支持 Obsidian 嵌套标签。大小写不同的标签（`Go` / `go`）归为同一个，网址用小写。**失**：标签网址可能是中文（`/tags/写作/`），浏览器可用但复制出来是百分号编码。

## 3．发布

### D11 `published/` 每次整体重建（镜像），而不是增量更新

- **得**：撤回、改回草稿、删除原稿、不再被引用的附件，都会自动从公开副本消失，逻辑只有一条。
- **失**：`draft` 与 `withdrawn` 的实际效果相同，区别只在语义；`published/` 里不能放手工维护的文件。撤回不会抹去 Git 历史（规划已说明）。

### D12 改 `slug` 的重定向靠手写 `redirect_from`，不自动检测

- **选择**：在文章里写 `redirect_from: 旧slug`，导出生成 `published/redirects.json`，Astro 据此生成跳转页。
- **放弃**：自动发现 slug 变化——那需要给每篇文章一个额外的稳定 ID。
- **失**：改 slug 时忘了写 `redirect_from`，旧地址直接 404，程序不会提醒。跳转是静态的 meta refresh 页面而非 HTTP 301（静态输出的限制；要 301 需改用 Vercel 适配器或 `vercel.json`）。

### D13 发布命令叫 `npm run release`

- `npm publish` 是 npm 的内置命令（发包到 npm 仓库），脚本若命名为 `publish` 还会被当作生命周期钩子，容易误触，所以避开。

### D14 发布命令只提交 `published/`，站点代码要自己提交

- 流程：检查 Git → 导出到 `.publish-tmp/` → 用临时副本构建 → 替换 `published/` → `git commit -- published` → `git push`。前三步任何失败都不会改动 `published/`、不提交、不推送。
- 暂存区有其它变更时直接停止；工作区有其它未提交变更时只提示。
- 导出结果与已提交的 `published/` 完全一致时直接结束，不再构建。**失**：内容没变时，`release` 不会顺带发现站点代码的构建错误；要检查构建用 `--dry-run`（它始终构建）。
- 提交信息里的新增 / 更新 / 移除数量按文件统计且关闭重命名检测，所以改 slug 记为「移除 1、新增 1」。
- **失**：`git push` 会连同你本地尚未推送的其它提交一起推上去；推送失败时提交留在本地，需手动处理后再推。

### D15 推送后自动核实 Vercel 部署，用 `vercel` CLI 按提交哈希查询

- **选择**：推送成功后，`npm run release` 每 5 秒执行一次 `vercel ls --format json`，找到本次提交对应的生产部署，等到 `READY` 才报告「上线完成」；`ERROR` / `CANCELED` 时以失败退出。最多等 5 分钟，`--no-wait` 可跳过。
- **放弃**：读 GitHub 上的提交状态（`gh api …/status`）——多依赖一层 Vercel 的 GitHub 集成回写；直接调 Vercel REST API——需要自己管理 token。
- **得**：「推送成功」与「上线完成」分开报告，部署失败能在命令里直接看到。
- **失**：依赖本机已登录的 `vercel` CLI 和 `.vercel/` 关联（换电脑要重新 `vercel login` 与 `vercel link`）。CLI 不可用或等待超时时只提示「部署状态未核实」并正常退出，不算失败——此时仍需人工确认。
- **注意**：实测 `vercel ls --meta githubCommitSha=…` 对未知哈希也会返回最近一次部署，所以程序拿到列表后按哈希再筛一遍，避免把上一次部署误报成本次上线。
- **现状（2026-10-01）**：Vercel 项目 `ozine-blog` 已关联 GitHub 仓库，推送 `main` 自动部署到 <https://ozine-blog.vercel.app>。

### D16 脚本用 Node 原生运行 TypeScript，不引入 tsx 等运行器

- **得**：少一个依赖。**失**：本机需要 Node ≥ 22.18（当前 24）；脚本里不能用 enum 等需要转译的语法。Vercel 只执行 `astro build`，不受影响。

## 4．站点

### D17 沿用 Astro 7 默认的 Sätteri 处理器，Callout 用自写的 hast 插件

- **背景**：Astro 7 的默认 Markdown 处理器从 remark/rehype 换成了原生的 Sätteri，remark 生态的现成 Callout 插件不能直接用。
- **放弃**：安装 `@astrojs/markdown-remark` 换回 unified 管线 + 现成插件。
- **得**：跟随默认路线，约 70 行插件，没有额外的运行时依赖。**失**：Sätteri 生态新、资料少；Callout 标题只支持纯文本；图标未做，只用颜色区分类型。

### D18 样式：Tailwind 4 + `@tailwindcss/typography`

- 正文排版用官方 typography 插件，而不是手写全部正文样式。**失**：默认风格偏英文排版，中文只做了行高和字体栈的调整。
- 深色模式跟随系统，没有手动切换按钮，站点自身不写客户端 JavaScript（唯一的脚本是访问统计，见 D23）。**失**：读者不能自行切换。
- 字体用系统字体栈，不加载 Web 字体：快，但不同系统观感不一致。
- 代码高亮用 Astro 内置的 Shiki，`github-light` / `github-dark` 双主题。

### D19 页面内容（待确认）

- 站点名暂用「Ozine」，简介、首页文案都是**占位内容**，集中在 `src/site.config.ts`。
- 首页：一句简介 + 全部文章（最初是最近 5 篇，见 D31）。
- 关于页已删除（D30）。最初它的正文直接写在 `about.astro` 里，不读取 Obsidian 的 `about.md`。
- 最初在规划的四个页面之外增加了 `/tags/` 和 `/tags/{标签}/`；它们和 `/posts/` 列表页后来都删除了（D32）。
- 文章目录只列二、三级标题：桌面端在右侧固定，手机端折叠在正文上方。

### D20 未配置 `site` 网址，未做 RSS / sitemap / Open Graph

- 域名未定，且这些不在首版范围内。定下域名后在 `astro.config.mjs` 加 `site`。

### D21 TypeScript 固定在 6.x

- 最新的 TypeScript 7 与 `@astrojs/check` 的 peer 依赖（`^5 || ^6`）冲突。

## 5．协作约定

### D22 提交信息：Conventional Commits + 中文说明

- **选择**：`<type>(<scope>): <中文说明>`，type 为 `feat` `fix` `docs` `style` `refactor` `test` `chore` `content`，scope 为 `export` / `site` / `publish`（可省略）。发布命令的自动提交使用 `content:`。
- **放弃**：全英文的 Conventional Commits（公开仓库更常见，但与项目的中文文档和报错不一致）；只按模块加前缀（规则少，但看不出改动性质）；纯中文前缀（不兼容现成工具）。
- **得**：类型关键字与 changelog 等工具兼容；文章发布与代码改动在历史里一眼可分。
- **失**：`content` 不是 Conventional Commits 的标准类型，严格的校验工具需要额外配置；中英混排。
- 定下规范时仓库尚未推送，已有的 3 个提交已按新规范改写。

### D23 访问统计用 Vercel Web Analytics（`@vercel/analytics`）

- **选择**：在 `src/layouts/Base.astro` 引入官方的 `<Analytics />` 组件，所有页面生效。
- **放弃**：不做统计；或用 Google Analytics、Plausible、Umami 等第三方或自建方案。
- **得**：与部署平台一体，零配置；不使用 Cookie，不需要 Cookie 提示；本地开发时不上报。
- **失**：站点不再是零客户端 JavaScript，每个页面多加载一个小脚本；统计数据绑定在 Vercel 上，换平台带不走；Hobby 套餐有每月事件数上限；带广告拦截的读者不会被统计到。
- **前提**：需要在 Vercel 项目的 Analytics 页面启用 Web Analytics，否则脚本请求会 404、没有数据。

### D24 配色先在独立的静态预览页里探索（`design/preview.html`）

- **选择**：在 `src/` 之外放一个不依赖构建的 HTML，用语义 token 展示配色初稿（紫调冷灰中性色 + 一个紫色强调色），确认后再改 `src/styles/global.css`。配色已经定稿并应用到站点（D26），预览页保留作以后试配色的地方。
- **放弃**：直接改 `global.css` 边改边看（最真实，但探索期会反复改动正式样式）；在 `src/pages/` 下加预览页（能复用真实排版，但会被构建并部署成公开页面）。
- **得**：不影响正式站点和部署；一个文件就能对比明暗两版，并实测对比度。
- **失**：预览页的排版是手写的近似，不是 Tailwind Typography 的真实输出；代码高亮是手工着色的示意，不是 Shiki 主题的实际效果；色值确认后还要再搬一次。

### D25 字体：正文霞鹜文楷（屏幕阅读版），标题思源宋体，随站点自托管

- **选择**：正文用 LXGW WenKai Screen，标题用 Noto Serif SC 600，代码仍用系统等宽字体。两款中文字体通过 npm 包（`lxgw-wenkai-screen-web`、`@fontsource/noto-serif-sc`）引入，由 Vite 打包进 `dist/`，和站点一起部署；都是按 `unicode-range` 分片的版本。
- **放弃**：继续全用系统字体（零加载、零依赖，但各系统观感不一，且没有个性）；正文也用思源宋体（更中性，和标题统一，但少了手写感）；从 jsDelivr 等公共 CDN 加载（不占构建产物，但读者的访问会暴露给第三方，CDN 不可用时字体就没了——预览页 `design/preview.html` 仍是这种方式）。
- **得**：各平台观感一致；文楷笔画柔和，长文耐读，气质贴近角色图；不依赖第三方服务。
- **失**：构建产物增加到约 21 MB，几乎全是字体（四百多个字体分片，读者只会下载用到的少数几个）；多了两个依赖，`node_modules` 增加约 140 MB；字体样式表放在 `<body>` 末尾、不挡首屏，代价是字体更晚才开始下载，先显示后备字体再跳变的时间会更长一点；一篇文章实际要下载十几个分片、约 0.5–1 MB，各分片各自到达、各自替换；思源宋体的包同时带了用不上的 woff 格式（约 4 MB，只占部署体积，读者不会下载）；霞鹜文楷的分片包只有常规字重，所以标题另配了宋体，正文里的粗体由浏览器合成；它字面偏小，根字号相应调到 17px。

### D26 配色：紫调冷灰 + 单一紫色强调色，全部做成语义 token

- **选择**：在 `src/styles/global.css` 的 `@theme` 里定义一组语义 token（页面、次级表面、边框、次要文字、正文、标题、强调色、装饰紫，以及五个提示块颜色），每个都是 `light-dark(亮色, 暗色)`。页面和组件只用这些 token，去掉了全部 Tailwind 原始色（`stone-*`）、`dark:` 变体和 `prose-invert`；Typography 插件的颜色变量也指向这些 token。取值与用法见 `docs/design.md`。
- **放弃**：原来的暖灰（stone）加青绿强调色；把紫色用作大面积底色（更「紫」，但不耐读）；提供手动的明暗切换开关（需要客户端脚本，而站点目前除访问统计外没有脚本）。
- **得**：换配色只改一处；明暗两版由同一个名字承担，不会漏改；正文类文字的对比度都在 4.5:1 以上（数值见 `docs/design.md`）。
- 定稿后的调整：紫色整体调浅。背景一度改成饱和度更高的紫并加了顶部光晕，随后撤回——确立了「阅读舒适是首要原则」，大面积的彩色底不耐读。底色回到紫灰，质感改由很淡的纸张颗粒和代码块、提示块的细微高光与投影来提供。现行取值以 `docs/design.md` 为准。
- **失**：颗粒让页面底色的实际亮度和 token 的标称值有一点偏差（暗色约亮 4/255），对比度表没有计入；颗粒层是一个铺满视口、带混合模式的固定图层，低端设备上滚动时多一点合成开销；明暗只能跟随系统，读者不能自己选；`light-dark()` 需要 2024 年之后的浏览器，更旧的浏览器上颜色声明会失效；提示块的 important 从紫色改成了梅红，和 Obsidian 里的观感不再一致。

### D27 角色图：从设定图抠出，放在 `pic/`，右下角常驻看板娘

- **选择**：新建根目录 `pic/`，存放设定图原图、由它生成的头像 / 全身立绘 / 网站图标，以及生成脚本 `pic/cut-character.mjs`。站点通过 Astro 的图片优化从 `pic/` 引入：头像放首页介绍区，全身立绘固定在所有页面右下角（只在宽屏显示），顶栏站名前只放一颗星。
- **放弃**：放在 `public/`（地址固定，但不经过图片优化，会原样发布五百多 KB 的 PNG）；放在 `src/assets/`（Astro 的惯例位置，但图片和它的来源、生成脚本就分散了）；请人重画一套网页专用的图（质量最好，但现在没有）。
- **得**：图片、来源和生成方式在一个目录里，换图只需替换原图并重跑脚本；页面实际加载的是按屏幕密度生成的 WebP（8–62 KB）。
- **失**：设定图只有 1280×720，抠出的图是放大过的，边缘偏软，首页头像在高分屏上不够锐利；抠图靠「与边缘连通的近白色算背景」，换一张图就要重新调裁切位置和要涂掉的标注线；网站图标是 SVG，较旧的 Safari 不显示；设定图原图进了公开仓库。

### D28 代码高亮主题保持 GitHub 明暗主题，只统一底色

- **选择**：Shiki 仍用 `github-light` / `github-dark`，但代码块底色不用主题自带的，改用 `--color-surface`。
- **放弃**：换成偏紫的主题（Rosé Pine、Catppuccin）。它们气质更贴，但亮色版里有几种颜色偏浅，没有核实对比度就不换。
- **得**：代码的可读性不变；代码块和页面是同一个色温。
- **失**：代码高亮的配色和整站的紫调没有呼应；GitHub 主题的各个颜色压在新底色上的对比度没有逐一计算。

### D29 顶栏去掉导航菜单，只留 GitHub 图标；加入一组纯 CSS 动效

- **选择**：顶栏右侧的「首页 · 文章 · 关于」换成一个指向 GitHub 主页（`https://github.com/realOzine`，取自仓库的远程地址）的图标。首页的「全部文章 →」改为始终显示，作为进入文章列表的入口。同时加入页面进入、看板娘浮动、星点闪烁、各处悬停反馈和跨页面淡入淡出，清单见 `docs/design.md` 第 6 节。
- **放弃**：保留导航菜单（规划里确认过的三个入口，见 `plan.md`）；用脚本做更复杂的动效（滚动触发、视差等）。
- **得**：顶栏更干净；动效全部是 CSS，站点仍然只有访问统计一个脚本；读者开了「减弱动态效果」时位移和循环动画都不播放。
- **失**：关于页失去了入口（随后被整页删除，见 D30）；从文章页回文章列表要先回首页再点「全部文章」；看板娘和星点是一直在动的元素，对部分读者可能是干扰；跨页面过渡在 Firefox 里不生效。

### D30 删除关于页

- **选择**：删除 `src/pages/about.astro`，站点不再有 `/about/`。
- **放弃**：保留页面并在页脚或首页补一个入口。
- **得**：没有无入口的孤立页面，也少一处占位内容要写。
- **失**：规划（`plan.md`）里确认的三个页面少了一个；访问 `/about/` 会得到 404，没有做重定向；自我介绍只剩首页的一句简介和 GitHub 链接。

### D31 首页列出全部文章，介绍区随滚动淡出

- **选择**：首页不再只显示最近 5 篇，而是列出全部文章，去掉「全部文章 →」和 `recentCount` 配置，原位置一度换成「标签 →」，标签页删除后也去掉了（D32）。介绍区在向上滚出视口时淡出，文章条目滚进视口时逐条浮现，都用 CSS 滚动驱动动画实现。
- **放弃**：真正的按需加载（滚到底再请求下一批）。那需要客户端脚本和分页数据接口，而文章只有标题和一行摘要，全部写进页面的成本很低。
- **得**：一页看完所有文章，没有分页和跳转；仍然没有新增脚本。
- **失**：文章很多时首页会变长、HTML 变大（每篇约几百字节）；`/posts/` 列表页和首页内容重复（随后删除，见 D32）；滚动效果在 Firefox 里没有；页面内容不满一屏时（比如现在只有一篇文章）没有滚动，看不到介绍区淡出。

### D32 删除 `/posts/` 列表页和标签页

- **选择**：删除 `/posts/`、`/tags/`、`/tags/{标签}/` 三种页面，以及只为它们服务的标签归并逻辑（`getTags`、`tagKey`）。站点只剩首页和文章详情页。文章详情页仍显示标签，但改成不可点击的文字（组件从 `TagLinks.astro` 改为 `Tags.astro`）。
- **放弃**：保留标签页，只删 `/posts/` 列表页；或删掉页面的同时也不再显示标签。
- **得**：没有重复和无入口的页面；结构最简单。
- **失**：读者不能按标签筛选文章，文章多了以后只能在首页的长列表里找；规划（`plan.md`）里的「文章列表页」和「标签浏览」不再存在；访问这几个旧地址会得到 404，没有做重定向；文章 frontmatter 里的 `tags` 仍会导出和校验，但只用于在文章页显示。

### D33 顶栏站名改用花体 Great Vibes

- **选择**：顶栏左上角的站名从「衬线体、全小写、字距 0.32em」改为英文花体 Great Vibes，按原样大小写显示（Ozine），字号放大到 `text-3xl`，不加字距。字体通过 npm 包 `@fontsource/great-vibes` 自托管，只引入拉丁字母一个分片，样式表并进主样式表。新增 token `--font-script`，只用于这一处。
- **放弃**：更纤细的 Pinyon Script（更华丽，但在这个字号下笔画太细、不好认）；装饰性衬线体如 Cinzel Decorative（好认，但和现在的衬线体差别不大）；把站名做成 SVG 字标（不用加载字体，但改站名就要重新出图）；页脚的站名也改成花体（小字号下花体不好认，保持不变）。
- **得**：站名有了辨识度；多下载的只有一个约 20 KB 的字体文件。
- **失**：站名不再和 `pic/logo.png` 的字标样式一致；多一个依赖；字体到达前先显示后备字体（macOS 上是系统花体，其他系统可能是普通字体），到达后会跳变一次；Great Vibes 只有拉丁字母，站名以后若改成中文，这个字体就不起作用了。
